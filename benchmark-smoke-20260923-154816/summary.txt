CAVEATS (carry these into any write-up)
  * Binaries are built with target-cpu=native: they are host-specific and
    NOT portable. Re-run on each machine you report.
  * CPU governor was 'schedutil', not 'performance': variance is inflated,
    and absolute timings are NOT comparable with a 'performance' run.
  * leanVM sizes its worker pool from available_parallelism() at startup and
    offers no override, so every timing here is a 16-thread figure.
    Nothing was pinned: set PIN_CPUS to fix it across machines.
  * A 0s idle cooldown preceded every target process. The balanced
    order reduces positional and predecessor bias but cannot guarantee equal
    package temperature; inspect t_start and host telemetry when publishing.
  * runs.csv carries t_start (epoch s) per run. Plot the metric against it
    before reporting. It also records load, selected-CPU frequency and the
    highest readable host temperature before and after every process. Empty
    telemetry fields mean the kernel exposed no portable sensor. drift.csv
    flags >15% early/late shifts but never removes observations.
  * The tree was dirty. source.patch records tracked changes only; untracked
    contents are omitted, so this run may not be exactly reconstructible.
  * A prover process calls zk_alloc::enable_arena(), which sets
    M_TRIM_THRESHOLD=-1: its RSS never decreases, so 'peak' means
    'high-water mark of a monotonic curve'. A verify-only process keeps
    normal malloc behaviour and its RSS is flat in the number of verifications.
  * Setup is paid once per process and is not persisted across restarts:
    every run re-executes the binary, so each target above paid it on all
    1 of its executions. It dominates total time; never fold it into
    per-update figures.
  * 'setup' is the leanVM circuit and nothing else.
    Committee key generation and signing ran in the separate fixture process
    before measurement. The prover row is one aggregator holding public keys
    and t ready-made signatures; the raw row is one relying-party verifier.
  * ML-DSA key generation and quorum signing ran in a separate fixture
    process. mldsa_raw_agg measures only record decode and verification.
  * Per-update samples within a run are not independent (shared allocator
    and cache state). The table's unit is the per-run median; samples.csv
    holds every raw observation if you need the pooled distribution.
  * sd / cv% / ci95 describe the spread BETWEEN runs, i.e. how reproducible
    the experiment is — not how much one operation varies. A single
    operation varies far more: see samples.csv, and the min/max columns of
    the *_total rows. Do not quote 'median ± ci95' as the cost of one call.
  * '<phase> / update' is a median and '<phase> total / run' is a sum, so
    total != n x per-update whenever the phase is skewed. Signing is: it
    has stragglers several times the median, and its total runs visibly
    above n x median. Verification is near-deterministic and does match.
  * Each signer target measures ONE member doing ONE signature per round.
    XMSS includes its durable slot burn (inactive journal generation plus
    sync_data) through SignerNode. ML-DSA is stateless and randomized, so
    it has no slot counter or persistence cost. Its crypto-sign row is not
    a complete signer protocol cost: one-statement-per-version state is absent.
    The measured prover/raw verifier receive t signatures prepared by the
    fixture process; neither produces signatures or holds secret keys.
  * Each keygen row is for ONE key. Only the XMSS signer has a slot-state
    row, for ONE durable counter.
    The fixture-mode prover/raw verifier report neither: the committee paid
    those costs outside the measured aggregator and verifier processes.
  * The XMSS signer cost applies unchanged to XMSS raw and PQ-SNARK records:
    those forms use the same XMSS statement, key and derived slot. ML-DSA is
    a separate raw alternative and its signer cost must not be substituted
    into the XMSS-based proof path.
  * Prove cost is driven by t, not by the number of updates. At small t
    the trace pads to a power of two, so prove time is a step function
    (t=5..=8 all cost the same); from a few dozen signers upward the
    linear term dominates. This sweep measured ONE t: t=3 at 2271.7 ms,
    i.e. 757.22 ms per aggregated signature -- a single point, not a
    slope, since it still carries the t-independent part of the proof.
    Re-run at a second t before quoting any per-signature figure, and
    do not extrapolate the step behaviour past small t.
